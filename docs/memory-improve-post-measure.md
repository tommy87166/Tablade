# 預覽記憶體：實作後在 Windows 量

docs/memory-improve.md 已經實作（`a1aaa8f`），只在 macOS 量過。這份是在會實際使用的 Windows 電腦上做驗收的步驟。

## 怎麼跑

在 repo 的資料夾裡（要有 `uv`）：

    git pull
    uv sync
    uv run python docs/memory-improve-measure.py
    uv run python docs/memory-improve-measure.py --threads 4

- 先確認 `git log -1` 是 `a1aaa8f` 或更新的版本。
- 兩個指令各跑一次：第一個用這台電腦全部的執行緒，第二個模擬 4 條執行緒的筆電。
- 每個大約 10～15 分鐘：會產生 40、80、160 個 zip（每個 12 萬行的假資料），每種檔數跑 6 步與 12 步兩種 Recipe。
- 記憶體 8 GB 以下的電腦加 `--files 20,40`。
- 照平常工作時的狀態跑（平常開著的程式不用關），可用記憶體才是實際的數字。
- 不連網路、不讀寫 repo 裡的檔。假資料放在系統的暫存資料夾，跑完就刪。

## 要貼回來的

兩次的報告各一整段，從「## 預覽記憶體的實測（實際操作 Session）」開始，到「跑完後系統可用記憶體」那一行為止。

- 報告裡沒有電腦名稱、使用者名稱或路徑。
- 最後一行「報告也存在：…」有暫存資料夾的路徑，不用貼。
- 有一列寫「失敗」的話，把畫面上那段錯誤訊息也一起貼。

## 每一步在量什麼

每種檔數、每種 Recipe 各開一個新的行程，照畫面上的操作走一次：

1. 載入資料及預覽。
2. 一步一步插入步驟，每插一步就看那一步（看畫面、取第一頁的資料）。
3. 連續點 30 次不同的步驟（每次看畫面、取第一頁）。
4. 改畫面上那一步的參數（最後一個篩選）。

## 看結果

| 項目 | 目標 | macOS 的結果（10 條執行緒，額度 256 MB） |
|---|---|---|
| 檔數從 40 變 160，「整個的峰值」 | 不變大 | 2.8～3.3 GB，不變大 |
| 16 條執行緒、12 步，「整個的峰值」 | 2.7 GB 以下 | 2.9～3.3 GB（10 條執行緒） |
| 4 條執行緒、12 步，「整個的峰值」 | 1.5 GB 以下 | 還沒量 |
| 6 步與 12 步的峰值差 | 差不到 1 成 | 差不到 1 成 |
| 點另一步（30 次平均） | 1 秒左右 | 12 步 1.1～1.3 秒、6 步 0.4 秒 |
| 改參數 | 0.3 秒以內 | 0.1～0.2 秒（40 個檔那兩列） |

- 「額度」那一欄是這台電腦算出來的樣本額度：全部執行緒時通常是 256 MB，`--threads 4` 時是 128 MB（可用記憶體很少時會更小）。
- 「樣本大小」比額度大約 27%（macOS：325 MB 對 256 MB），這是已知的：一行一欄的文字檔，讀前 2,000 行量出來的一行大小偏小。
- macOS 的峰值比目標高，一半是樣本比額度大，一半是多留的「畫面上那一步的輸入」。Windows 也高出目標的話，打算把這種文字檔量出來的一行大小乘 1.25 再分配（樣本回到約 256 MB），或把額度改小；要看兩次的數字再決定。
- 80、160 個檔的「改參數」在 macOS 是 1.6 秒：那是修正之前量的（沒有先備好那一步的輸入），現在應該跟 40 個檔一樣是 0.1～0.2 秒。Windows 上不是的話要再查。

### 看到的

1. **峰值不隨檔數、步驟數變大**：第 1、第 2 部分的主要目的在 Windows 上成立。檔數 4 倍、步驟 2 倍，峰值最多多 1 成。
2. **峰值比目標高，而且比 macOS 高更多**（16 條：3.8～4.1 GB 對 macOS 的 2.9～3.3 GB）。
   - 樣本比額度大 27%（325 MB 對 256 MB、163 MB 對 128 MB），和 macOS 一樣，是已知的一行大小偏小。
   - 比 macOS 多出來的，應該是實作前量到的「Windows 上每多一條執行緒約多 55 MB」（16 條對 4 條約 0.66 GB）。這次兩種執行緒數的額度不一樣（256 對 128 MB），沒辦法直接相減驗證。
   - 「整個的峰值」比「插步驟時的峰值」高很多（16 條：2.3 GB 對 3.8 GB；4 條：1.2 GB 對 1.9 GB），所以最高點是在**點另一步或改參數**的時候，不是插步驟的時候。要壓峰值，先看點另一步時同時留著幾張表（畫面上那一步、它的輸入、重算時的中間表）。
3. **把樣本拉回額度能不能達到目標**（粗估，沒有實測；固定部分用的是實作前在同一台電腦量到的數字）：把跟著樣本變的部分乘 256 / 325 ≈ 0.79。
   - 4 條：固定部分約 0.25 GB，(1.93 − 0.25) × 0.79 + 0.25 ≈ 1.6 GB，接近 1.5 GB，可能還差一點。
   - 16 條：固定部分約 0.9 GB，(4.06 − 0.9) × 0.79 + 0.9 ≈ 3.4 GB，還是比 2.7 GB 高很多。只修一行的大小不夠，16 條的目標要嘛把額度再改小，要嘛把目標改成依執行緒數（例如加上每條執行緒 55 MB）。
4. **改參數的時間跟著檔數變長**：40 個檔 0.13～0.24 秒、80 個檔 0.26～0.33 秒、160 個檔 0.41～0.52 秒（兩種執行緒數都一樣），樣本大小是一樣的。已經不是修正前的 1.6 秒，「先備好那一步的輸入」有作用；但時間跟檔數成正比，看起來是每個來源檔各跑一次的固定成本（`per_file` 的步驟、或每個檔各做一次的檢查）。照上面「看結果」的說明，這要再查。
5. **點另一步也跟著檔數變長**（12 步：1.13 → 1.43 秒；6 步：0.49 → 0.76 秒），可能和第 4 點是同一個原因。
6. **載入的時間跟檔數成正比**（40 個檔約 8 秒、160 個檔約 31 秒），兩種執行緒數一樣：時間花在讀 zip、轉碼，不是 Polars 的計算。這次的計畫沒有要改這個。
