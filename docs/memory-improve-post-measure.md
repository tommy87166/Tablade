# 預覽記憶體：實作後在 Windows 量

docs/memory-improve.md 已經實作（`a1aaa8f`），只在 macOS 量過。這份是在會實際使用的 Windows 電腦上做驗收的步驟。

## 怎麼跑

在 repo 的資料夾裡（要有 `uv`）：

    git pull
    uv sync
    uv run python docs/memory-improve-measure.py
    uv run python docs/memory-improve-measure.py --threads 4

- 先確認 `git log -1` 是 `a1aaa8f` 或更新的版本。
- 兩個指令各跑一次：第一個用這台電腦全部的執行緒，第二個模擬 4 條執行緒的筆電。
- 每個大約 10～15 分鐘：會產生 40、80、160 個 zip（每個 12 萬行的假資料），每種檔數跑 6 步與 12 步兩種 Recipe。
- 記憶體 8 GB 以下的電腦加 `--files 20,40`。
- 照平常工作時的狀態跑（平常開著的程式不用關），可用記憶體才是實際的數字。
- 不連網路、不讀寫 repo 裡的檔。假資料放在系統的暫存資料夾，跑完就刪。

## 要貼回來的

兩次的報告各一整段，從「## 預覽記憶體的實測（實際操作 Session）」開始，到「跑完後系統可用記憶體」那一行為止。

- 報告裡沒有電腦名稱、使用者名稱或路徑。
- 最後一行「報告也存在：…」有暫存資料夾的路徑，不用貼。
- 有一列寫「失敗」的話，把畫面上那段錯誤訊息也一起貼。

## 每一步在量什麼

每種檔數、每種 Recipe 各開一個新的行程，照畫面上的操作走一次：

1. 載入資料及預覽。
2. 一步一步插入步驟，每插一步就看那一步（看畫面、取第一頁的資料）。
3. 連續點 30 次不同的步驟（每次看畫面、取第一頁）。
4. 改畫面上那一步的參數（最後一個篩選）。

### 看到的

1. **峰值不隨檔數、步驟數變大**：第 1、第 2 部分的主要目的在 Windows 上成立。檔數 4 倍、步驟 2 倍，峰值最多多 1 成。
2. **峰值比目標高，而且比 macOS 高更多**（16 條：3.8～4.1 GB 對 macOS 的 2.9～3.3 GB）。
   - 樣本比額度大 27%（325 MB 對 256 MB、163 MB 對 128 MB），和 macOS 一樣，是已知的一行大小偏小。
   - 比 macOS 多出來的，應該是實作前量到的「Windows 上每多一條執行緒約多 55 MB」（16 條對 4 條約 0.66 GB）。這次兩種執行緒數的額度不一樣（256 對 128 MB），沒辦法直接相減驗證。
   - 「整個的峰值」比「插步驟時的峰值」高很多（16 條：2.3 GB 對 3.8 GB；4 條：1.2 GB 對 1.9 GB），所以最高點是在**點另一步或改參數**的時候，不是插步驟的時候。要壓峰值，先看點另一步時同時留著幾張表（畫面上那一步、它的輸入、重算時的中間表）。
3. **把樣本拉回額度能不能達到目標**（粗估，沒有實測；固定部分用的是實作前在同一台電腦量到的數字）：把跟著樣本變的部分乘 256 / 325 ≈ 0.79。
   - 4 條：固定部分約 0.25 GB，(1.93 − 0.25) × 0.79 + 0.25 ≈ 1.6 GB，接近 1.5 GB，可能還差一點。
   - 16 條：固定部分約 0.9 GB，(4.06 − 0.9) × 0.79 + 0.9 ≈ 3.4 GB，還是比 2.7 GB 高很多。只修一行的大小不夠，16 條的目標要嘛把額度再改小，要嘛把目標改成依執行緒數（例如加上每條執行緒 55 MB）。
4. **改參數的時間跟著檔數變長**：40 個檔 0.13～0.24 秒、80 個檔 0.26～0.33 秒、160 個檔 0.41～0.52 秒（兩種執行緒數都一樣），樣本大小是一樣的。已經不是修正前的 1.6 秒，「先備好那一步的輸入」有作用；但時間跟檔數成正比，看起來是每個來源檔各跑一次的固定成本（`per_file` 的步驟、或每個檔各做一次的檢查）。照上面「看結果」的說明，這要再查。
5. **點另一步也跟著檔數變長**（12 步：1.13 → 1.43 秒；6 步：0.49 → 0.76 秒），可能和第 4 點是同一個原因。
6. **載入的時間跟檔數成正比**（40 個檔約 8 秒、160 個檔約 31 秒），兩種執行緒數一樣：時間花在讀 zip、轉碼，不是 Polars 的計算。這次的計畫沒有要改這個。

## 審查兩邊的結果（2026-11-20）

主要的目的達到了：峰值不隨檔數、步驟數變大，兩個平台都成立；改參數的修正也有效。沒達到的是峰值的絕對值，另外找到時間隨檔數變長的原因。

### 1. 樣本比額度大 27%：原因找到了，是量一行大小的方式

- `_line_sizes`（`ingest/sources.py`）是對**單一個檔**的前 2,000 行量 `estimated_size()`。單一個檔的表裡，`__source_file` 那一欄整欄是同一個值，整張表的 `estimated_size()` 幾乎不算它。樣本是很多個檔接起來的，這一欄就照每列一份算。
- 實測（這份假資料，一個檔）：整張表的 `estimated_size()` 是每行 126 bytes；各欄分開量再相加是 160 bytes（`__source_file` 34、`__line_no` 8、`line` 118）。樣本實際是每行 160 bytes。160 ÷ 126＝1.27，就是多出來的 27%。
- 修法：`_line_sizes` 裡改成各欄的 `estimated_size()` 相加（一行）。不用乘 1.25 這種修正係數。樣本會回到約 256 MB／128 MB，行數約 168 萬／84 萬。
- 這不只影響一行一欄的文字檔：CSV、Parquet 的樣本只要是好幾個檔接起來的，都會多算不到這一欄（檔名越長差越多）。

### 2. 峰值比目標高：目標訂得太低，是審查時估錯的

docs/memory-improve.md「驗收」的目標（16 條 2.7 GB、4 條 1.5 GB）是用實作前的模擬加 0.3～0.5 GB 訂的。實際上多出來的比這個多：

- 模擬只留樣本與畫面上那一張；實作照計畫另外留「最後一步」與「畫面上那一步的輸入」兩張，各約一份樣本的大小。
- 實際載入後的行程比模擬的大（Windows 16 條：0.7～0.9 GB；模擬是先存成 Parquet 再讀回來，同樣大小的樣本約 0.45 GB）。
- 最高點在連續點另一步的時候（比插步驟時高 1.2～1.5 GB）：這時候同時有樣本、最後一步、重算中的兩張表與計算的暫時記憶體。

四組數字都符合這個算法：**峰值 ≈ 0.4 GB＋每條執行緒的固定部分（Windows 約 55 MB、macOS 約 30 MB）＋樣本 × 7.5**。

| | 樣本 | 算出來 | 實測（12 步） |
|---|---|---|---|
| Windows 16 條 | 325 MB | 3.7 GB | 3.8～4.1 GB |
| Windows 4 條 | 163 MB | 1.8 GB | 1.9 GB |
| macOS 10 條 | 325 MB | 3.1 GB | 3.3～3.4 GB |
| macOS 4 條 | 163 MB | 1.7 GB | 1.8～1.9 GB |

- 第 1 點修好後（樣本回到額度），照同一個算法是 Windows 16 條約 3.2 GB、4 條約 1.6 GB。
- 建議把驗收的目標改成這個算法（16 條 3.3 GB 以下、4 條 1.7 GB 以下），不把額度再改小：
  - 16 條執行緒的電腦記憶體通常也多（這台可用 17 GB，3.2 GB 不到 2 成）。
  - 4 條、額度 128 MB 要可用記憶體 2.6 GB 以上才會給到，1.6 GB 放得下；可用更少時額度會降到 82 MB，峰值約 1.2 GB。
  - 改之前沒有上限（300 個大檔 30 GB 以上）。
- 想再壓低的話，下一個可以動的是「最後一步」那張表：只有一個階段、沒有別的階段讀它的時候可以不留（只存列數與欄位），大約少一份樣本（額度 256 MB 時約 0.3 GB）；代價是點「輸出資料」要重算。這次不建議做。

### 3. 改參數、點另一步的時間跟著檔數變長：每次都重新檢查每個檔

- 原因不在這次的改動，是原本就有的：`_source_key`（`session.py:1116`）每次都把檔案清單展開、對每個檔做 `stat` 與 `resolve`，用來判斷檔案有沒有變；而一次 `state()` 裡它會被呼叫 10～11 次（每次 `_compute`、`_stage_input` 都會問一次）。
- 實測（macOS，`cProfile`）：一次 `state()`，40 個檔 39 毫秒、160 個檔 138 毫秒；160 個檔時 `_source_key` 被呼叫 11 次、共 152 毫秒，裡面是 5,624 次 `stat` 與 20,840 次 `lstat`。
- Windows 上 `stat` 比較慢，所以差得更明顯（改參數：40 個檔 0.13～0.24 秒，160 個檔 0.41～0.52 秒）。檔數再多會繼續變長：照比例 500 個檔時，Windows 上每個動作多 1 秒左右。
- 修法：一次 API 呼叫裡只算一次（例如在拿到鎖的那一次呼叫期間記住結果），11 次變 1 次。這是另一項修正，不屬於這次的計畫，但對「很多個檔」的情境影響很直接，建議接著做。

### 修正 3：檢查檔案有沒有變，一次呼叫只做一次

**修改處**

| 檔 | 位置 | 改什麼 |

不用改的：36 個 `with self._lock:` 都照舊（`_CallLock` 有 `__enter__`／`__exit__`）；`api.py` 沒有直接碰鎖。

**實作方式**

    class _CallLock:
        """可重入的鎖；最外層放開時呼叫 on_release（清掉這次呼叫記住的東西）。"""

        def __init__(self, on_release):
            self._lock = threading.RLock()
            self._depth = 0
            self._on_release = on_release

        def __enter__(self):
            self._lock.acquire()
            self._depth += 1
            return self

        def __exit__(self, *exc):
            self._depth -= 1
            if self._depth == 0:
                self._on_release()
            self._lock.release()

`_source_key` 開頭：

    memo_key = json.dumps([stage["uid"], str(self.base_dir), stage["input"]], ensure_ascii=False, sort_keys=True, default=str)
    if memo_key in self._key_memo:
        return self._key_memo[memo_key]
    …（原本的算法）…
    self._key_memo[memo_key] = key

- 「一次呼叫」＝從最外層的 `with self._lock:` 進去到出來。畫面每做一個動作，`api.py` 是先呼叫那個動作、再呼叫 `state()`，是兩次，所以檔案有變最晚在下一次 `state()` 就會發現，和現在一樣。
- 記住的 key 包含階段的代號、基準資料夾、這個階段的讀取設定：同一次呼叫裡改了檔案清單、編碼這些設定（`set_input`）會重算，不會拿到舊的。
- `_forget_keys` 要寫成方法（裡面才讀 `self._key_memo`），不要把字典的 `clear` 直接傳給鎖：`_reset()`（`session.py:552`）會在拿著鎖的時候重新呼叫 `__init__()`，鎖和字典都會換成新的。舊的鎖放開時呼叫 `_forget_keys`，清到的是新的字典，沒有影響。
- 只在拿著鎖的時候讀寫 `_key_memo`，不用另外處理多執行緒。
- 順便的好處：同一次呼叫裡的答案一致。現在如果檔案剛好在 `state()` 算到一半時被改，前半認為已載入、後半認為要重新載入。
- 這次不動 `check_entries`（`state()` 裡 3 次）與 `_zip_state`：它們也會查每個檔，但只佔約 1/8（160 個檔時 18 毫秒對 152 毫秒）。之後還嫌慢，可以用同一個機制。

| 修正後 | 48 毫秒 | 被問 100 次，算 10 次 |

**測試**

- 一次 `state()` 裡，展開檔案清單（`tablade.session.expand`）被呼叫的次數不超過「讀檔的階段數 × 清單的項目數」再加 `check_entries` 的那幾次（用 `monkeypatch` 包一層計數）；現在是 10 倍以上。
